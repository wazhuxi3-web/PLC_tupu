## 分析结果的含义

静态图回答“程序中谁可能影响谁”。仅凭静态路径不能判断某次扫描实际走了哪条分支，不能回答现场某个信号当前为何为 0 或 1。

例如一段程序包含 `A I0.0`、`AN M0.1`、`= Q0.0`，结果应记录 I0.0 和 M0.1 均参与 Q0.0 的逻辑，并保留否定运算和原始指令。图中的箭头本身不足以表达完整布尔条件。

边至少区分：调用、读取、写入、输入参数映射、输出参数映射、数据依赖和控制依赖。直接证据、保守推导、未解析关系须可区分，不用没有依据的百分比表示可信程度。

查询不到路径时应显示“在当前已解析范围内未发现路径”。如果存在未解析指令或达到遍历上限，还应标出结果不完整，不能据此断言不存在影响。

## 分层方案

```text
完整 STEP7 工程 ── 工程读取适配器 ──┐
                                   ├─ 统一程序模型 ─ 分析引擎 ─ 查询服务 ─ 图谱界面
AWL/STL 导出文件 ─ 源码读取适配器 ──┘                            │
                                                               └─ Dify 工作流（后续）
```

1. 读取层提取块、接口、符号、指令、注释及来源位置。
2. 统一程序模型隔离不同文件格式，避免界面直接依赖第三方解析库对象。
3. 分析层构建调用关系、读写索引、参数绑定及数据/控制依赖。
4. 查询层提供稳定的结构化查询，供界面与后续 Dify 共用。
5. 展示层负责搜索、过滤、展开、路径高亮和源码定位。

初期可用进程内图结构和本地结构化存储；是否引入专用图数据库由真实规模和查询性能决定。

官方 README 列出 STEP7 V5.5 `.S7P` 读取、MC7 到 AWL/DB 转换及多种 S7 块支持，因此优先评估为完整工程读取适配器。README 的支持声明不能替代对本项目样本的兼容性验证。

README 明确描述从 PLC IL 程序生成输入与输出变量的依赖。适合作为分析方法和测试思路的参考；尚未核验其解析器对本项目的指令、调用上下文和寻址方式的覆盖，不能直接认定其为完整分析引擎。

来源：[官方仓库](https://github.com/zeyuid/ARES)。

## 统一程序模型的最低要求

| 对象 | 必须保留的信息 |
| --- | --- |
| 工程快照 | 工程标识、快照标识、输入摘要、解析器版本、导入结果 |
| 程序块 | 块类型/编号、接口、名称、注释、来源 |
| 变量 | 原始写法、规范地址、符号、类型、作用域、实例归属 |
| 指令 | 操作码、操作数、所在块/Network、源码位置 |
| 调用点 | 调用位置、目标块、实例 DB、参数绑定、解析状态 |
| 图边 | 类型、起终点、产生依据、源指令、适用调用上下文 |
| 诊断 | 不支持的指令或寻址、位置、原因、影响范围 |

不能只按变量名合并节点。同名 TEMP 在不同块或调用上下文中须隔离；不同实例 DB 的 STAT 须隔离；同一 FC 的多处调用须保留各自的参数绑定。全局地址则应在同一工程快照中保持一致。

需要显式处理字节、字和双字地址重叠；如果某类重叠尚不支持，应报告分析范围，不能把重叠地址完全视为独立变量。

## 实施顺序与验收关口

### M0：用样本验证读取链路

- 确定输入平台、格式、编码及符号资料。
- 读取块清单，并与原始工程或导出文件对照。
- 检查一个包含调用参数的块、一个 FB 实例以及一个 DB。
- 输出明确的支持范围与失败清单。

通过标准：真实样本中的目标块和调用信息可以复现读取；有明确失败报告。未获得真实样本时，只能标记为演示验证。

### M1：调用图与变量交叉引用

- 实现工程/块浏览、调用图及读写检索。
- 每个查询结果能定位来源。
- 缺失块及未知调用目标保留占位并给出诊断。

通过标准：人工选定的调用和变量读写位置与工具输出一致；重复调用不被合并掉。

### M2：参数流闭环

- 优先覆盖样本实际使用的直接寻址、布尔逻辑、装载/传送及常用运算。
- 依据块接口解析 IN、OUT、IN_OUT，连接调用前后参数关系。
- 逐步加入控制流与块内数据流分析；不能把一个 Network 中出现的所有变量互相连线。
- 实现上下游追踪、两点路径和局部子图。
- 对间接寻址、AR1/AR2、ANY、动态 DB、未知系统块等尚未支持的内容输出诊断。

通过标准：至少覆盖直接赋值、多输入逻辑、跨块传参、多次调用隔离、多实例隔离、循环依赖、未解析关系和路径截断；测试既检查应存在的边，也检查不应产生的跨调用伪路径。

### M3：真实工程验收

- 由用户指定关注的变量或输出，逐项核对来源和影响路径。
- 记录块数、指令数、导入时间、查询时间和未解析范围。
- 对选定且属于支持范围的路径验收；不以一张演示图代表完整工程已经支持。

### M4：Dify 工作流集成（后续）

- Dify 提取查询意图及参数，调用分析服务。
- 服务返回局部图、源程序证据和完整性信息。
- 模型基于这些结果生成解释，界面根据返回的节点/边展示图谱。
- 具体图表呈现方式在本阶段按用户的“图标”原意确认。

Dify 官方 HTTP Request 节点支持调用外部 API，因此可以把 HTTP 查询作为集成边界，不必把 MCP 列为首版前置依赖。此处是架构方案，尚未配置工作流或验证部署网络。

来源：[Dify HTTP Request 文档](https://docs.dify.ai/en/cloud/use-dify/nodes/http-request)。
