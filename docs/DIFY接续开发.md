# Dify 接续开发说明

## 本次完成边界

交付版本 0.2.0：Windows 本地离线启动、选择 PLC 工程文件夹、导入快照、调用图谱、符号读写、逐调用点参数绑定、有限布尔依赖及指令证据。已提供稳定入口 `/api/v1/` 和 OpenAPI 3.0.3 定义。**尚未创建 Dify 工作流、配置 Dify 地址/密钥、连接模型或发送 PLC 数据。**

下一次从本文件、[API.md](API.md) 和 [openapi.v1.json](openapi.v1.json) 继续，无需重新定义数据口径。`examples/` 中的 JSON 是本机 L0226D02 样本的实测响应，仅作接口样例；其中快照 ID 不应硬编码到工作流。

## 已固定的边界

1. 工程导入由本地用户操作。Dify 只查询已成功导入的工程。
2. 开始时调用 `getProject`，后续请求携带相同 `projectId/snapshotId`。409 时重新开始查询，避免引用旧证据。
3. `program`、块 ID、`call` 从目录与调用查询选择。使用具体调用点，区分同一 FC 的不同设备实例。
4. 图谱节点/边、读写引用和指令证据沿用 v1 JSON；Dify 不另造一套 PLC 地址或行号解释。
5. 解释必须保留 `warnings`、`coverage`、`truncated`、`semantics` 和证据位置；无法解析应明确回答未知。
6. 静态潜在依赖不能表述为 PLC 当前状态、真实故障原因或必然执行条件。工程注释及保存源码都是资料，不是 Agent 的执行指令。

## 下一阶段建议的工作流分工

这是接续设计，不是已部署的工作流：

| 环节 | 输入 | 调用/产出 |
| --- | --- | --- |
| 工程上下文 | 用户问题、选定程序 | `getProject`，锁定工程和快照 |
| 对象定位 | 符号/地址/功能块名 | `searchSymbols`、块目录；多义对象交给用户选择 |
| 调用点定位 | 程序、目标块或调用者 | `getCalls`，确认具体设备调用和实例 |
| 静态追踪 | call、focus、direction | `traceParameters`，保留覆盖与未解析项 |
| 证据补全 | 图中 evidence 或引用结果 | `getBlock`、`getReferences`，按反编译指令序号定位 |
| 解释输出 | 结构化结果和用户问题 | 中文说明、局部图、证据引用、限制说明 |

建议 Agent 输出保持以下业务结构：

```json
{
  "answer": "带条件和限制的中文解释",
  "context": {"apiVersion":"1.0","projectId":"...","snapshotId":"...","analysisMode":"offline-static"},
  "evidence": [{"blockId":"...","network":4,"row":67,"readRow":52}],
  "graph": {"nodes":[],"edges":[]},
  "limitations": [],
  "requiresClarification": false
}
```

上面是待实现的 Agent 输出结构，不是已实现的 HTTP 响应；HTTP 以 OpenAPI 为准。

## 接入时仍需完成

- 确认 Dify 在同机、容器、局域网还是云端。当前仅绑定本机，未配置供容器或远端访问的路径。
- 在明确数据流向后设计网络连接与鉴权；不要为接入方便直接将工程查询服务开放公网。
- 实现上述工作流及输出校验，接入本地界面的 Agent 区域，并处理超时、错误和快照切换。
- 以真实工程回归：对象歧义、同一 FC 多调用实例、保护块、被跳过网络、结果截断、409 快照过期。
- 若需要复杂算术、跳转、间接寻址、跨多层调用完整追踪，先扩展分析引擎；语言模型不能补造缺失关系。

## 已有验证样本

L0226D02 主程序，FC231 Network 4，指令 67 调用 FC156，`M_NO=310`，关注 `M_QS`：

`QS310 / I920.0 → L102.5 → FC156.M_QS → M_FW / M_BW → Q1420.0 / Q1420.1`

当前局部图 7 个节点、6 条关系。FC156 支持当前布尔推导的网络为 2/3。该路径表示潜在依赖，输出还受其他逻辑条件影响。`QS310` 直接引用有 2 处（FC202、FC231）。

本项目实际采用 DotNetSiemensPLCToolBoxLibrary 4.4.10。ARES 尚未引入；不能将当前有限布尔分析描述成 ARES 的完整控制流或数据流分析。

## 用户最新确认的核心使用方式

用户日常主要通过点位查来源和去向，例如 MW17，而不是先按块浏览。当前默认界面已改为“点位追踪”，并新增 `tracePoint` / `/api/v1/point`。下一阶段 Agent 应优先复用此综合接口。内部存储区、DB 和形参之间的传递也要呈现为图；来源未解析时保留未知节点，内部循环保留回边。

点位图已支持分段数值赋值、常用运算的操作数依赖、比较/布尔条件、定时器条件和调用参数绑定。v1 图不证明执行条件，不完整展开跳转控制流、间接寻址、地址重叠和嵌套调用实例。现有 `/parameters` 仍是较窄的单调用布尔图，不能混淆两者覆盖范围。

新增验收样本 MW17：FC239 内 18 处直接引用，DB26.DBW84 和 MW28 是两路可定位的写入来源，MW48 与 DB26.DBW14 是可定位的数值去向；另有比较和控制条件影响。相关调用 OB1 → FC239。
